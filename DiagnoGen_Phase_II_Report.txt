Abstract
DiagnoGen is an AI-assisted healthcare support system designed to accept user symptoms and generate preliminary disease predictions through a modular web architecture. The complete product vision includes natural language processing, prediction, confidence scoring, AI-generated healthcare guidance, emergency symptom detection, history storage and production deployment support. Phase-II intentionally implements only the core vertical slice required to prove the system path from symptom entry to disease prediction.
This report documents the Phase-II implementation of FR-01 User Symptom Input and FR-04 Disease Prediction. The selected scope is technically defensible because these requirements establish the minimum useful flow: a user provides symptoms, the backend processes the request, the machine learning module predicts a disease class, and the result can be returned for display. All other features remain planned for subsequent phases and are treated as architecture-ready but not claimed as implemented.

1. Project Overview
DiagnoGen is planned as a healthcare assistance platform that helps users describe symptoms and receive preliminary disease prediction support. The system is not positioned as a replacement for clinical diagnosis; instead, it provides structured assistance that can guide early awareness and encourage appropriate medical consultation.
The architecture separates the user interface, API gateway, AI processing components, data layer and deployment layer. This separation is important because healthcare software must remain maintainable, testable and extensible. A narrow Phase-II implementation allows the team to validate the most important technical path before adding higher-risk modules such as emergency alerting, generative AI guidance and prediction history storage.
2. Problem Statement
Users commonly describe symptoms in informal language, while machine learning systems require structured inputs. Without a working bridge between the user interface and prediction module, DiagnoGen would remain only an architecture proposal. Phase-II therefore addresses the problem of creating a simple user input path and connecting it to a disease prediction model in a way that can be tested, demonstrated and extended.
Phase-II Problem Focus: Build a reliable minimum implementation that accepts symptom input and returns a disease prediction, while avoiding unsupported claims about advanced healthcare guidance or emergency decision-making.
3. Phase-II Objectives and Scope

The DiagnoGen architecture is organized into five major layers: frontend, API gateway, AI processing, data and deployment. Phase-II uses the frontend layer for symptom input, the API layer for request handling and the AI processing layer for disease prediction. Data storage, monitoring, cloud deployment, emergency detection and generative AI guidance remain part of the future-ready architecture.

7. Implementation Design
7.1 FR-01 User Symptom Input
The user symptom input module is the first visible interaction in DiagnoGen. Its design priority is clarity: users should be able to describe symptoms naturally without understanding dataset fields, model features or backend endpoints.
* Provide a visible symptom entry field in the Streamlit interface.
* Accept ordinary symptom descriptions such as fever, cough, headache or fatigue combinations.
* Prevent blank submissions through supporting validation behavior.
* Package the symptom text into a backend request that can be processed by the prediction service.
Design Boundary: Although validation supports the input flow, FR-02 is not counted as an independently completed requirement in Phase-II.
7.2 FR-04 Disease Prediction
The disease prediction module receives the processed symptom representation and passes it to a machine learning classifier. The project technology stack identifies Random Forest as the primary disease prediction algorithm because it provides stable performance and reduces the risk of overfitting compared with a single decision tree.
* Transform the processed symptom information into the model-ready feature structure.
* Use the trained Random Forest classifier to predict a possible disease class.
* Return the predicted label to the API response path.
* Present the output as preliminary decision support rather than medical diagnosis.

11. Limitations and Future Work
The Phase-II implementation is intentionally narrow. It demonstrates the core interaction but does not yet represent the full healthcare system described in the architecture and requirements documents.
Deferred AreaReason for DeferralFuture Phase DirectionNLP-Based Symptom ExtractionRequires stronger text normalization and medical vocabulary handling.Introduce tokenization, symptom extraction and controlled vocabulary mapping.Confidence Score GenerationRequires calibrated model output and evaluation methodology.Add probability handling or confidence scoring once dataset evaluation is stable.AI Response GenerationRequires safety review and careful healthcare wording.Generate structured guidance with disclaimers and prompt safety controls.Emergency DetectionHigh clinical risk if implemented prematurely.Define critical symptom rules and escalation messaging with strict disclaimers.Prediction History StorageRequires privacy-aware storage design.Add authenticated users, secure records and audit-friendly persistence.
12. Conclusion
Phase-II successfully defines a focused implementation path for DiagnoGen by selecting and documenting two high-priority functional requirements: user symptom input and disease prediction. This creates a measurable core prototype and avoids overclaiming unfinished modules. The resulting system path supports future expansion into NLP extraction, confidence scoring, AI guidance, emergency alerting, prediction history and production deployment.
